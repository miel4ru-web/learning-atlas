# Learning Atlas

브라우저에서 도는 로컬 우선 간격 반복 학습 도구. 데이터는 기본적으로 이 브라우저의
IndexedDB에만 저장된다(전용 서버 없음). React 19 + TypeScript + Vite.

[GitHub Pages로 배포](https://miel4ru-web.github.io/learning-atlas/)되며, 기기 간
동기화가 필요하면 "데이터" 탭에서 GitHub 저장소를 데이터베이스처럼 쓰는 수동 동기화를
켤 수 있다(v30, 아래 "GitHub 동기화" 참고). 이 리포지토리는 퍼블릭이라 동기화를 켜면
개인 학습 로그도 함께 커밋된다 — 알고 켜는 기능이다.

## 설계 원칙 — 이벤트 소싱

영속화하는 건 세 가지뿐이다.

| 스토어 | 내용 |
| --- | --- |
| `items` | 카드 정의 (플래시카드 / 빈칸 / 4지선다 / 코드 / 단답형 / 자기 설명) |
| `kcs` | 지식 요소(Knowledge Component)와 선수지식 DAG |
| `interactions` | 채점 로그 — **append-only, 수정·삭제 안 함** |
| `settings` | 키별 단일 레코드 두 개 — 재적합한 FSRS 파라미터(`scheduler`), 백로그·휴가 모드 설정(`studyPrefs`). 둘 다 선택 |
| `sessions` | 학습 세션 기록 — 시작 시각·예산·그때 고정한 카드 순서. 진행 상황은 여기 없다(로그에서 센다) |

FSRS 카드 상태, Elo 숙달도, 캘리브레이션, 예측 회상률 등 **파생 상태는 저장하지
않는다**. 매번 `interactions` 로그를 재생해 계산한다. 덕분에 스케줄러를 바꿔
끼우거나(SM-2 → FSRS, 파라미터 재적합) 백업을 복원해도 과거 로그 전체가 새
기준으로 재계산된다.

## 기능 (v0 → v30)

- **v0** FSRS-6 스케줄러(`ts-fsrs`), 이벤트 소싱 플래시카드 큐
- **v1** KC 선수지식 DAG, Elo 숙달도 추정(θ·b), 세션 오케스트레이터, 응답 전 자신감 입력
- **v2** 빈칸/4지선다/코드 활동 타입, 오답 원인 태깅, leech 격리·재출제, 메타인지 캘리브레이션
- **v3** 분석 대시보드, 오프라인 시뮬레이션(log loss·RMSE), 개인 로그로 FSRS 21개 파라미터 재적합(Hooke–Jeeves)
- **v4** "바람직한 어려움" 밴드(예측 회상률 0.70–0.85) 기반 문항 선택 — v1부터 계산만 되던 Elo 문항 난이도를 여기서 활용
- **v5** 전체 데이터 JSON 내보내기 / 가져오기(병합·완전교체), 파일 검증
- **v6** 탭 셸 구조 — 전역 상태(`AtlasProvider`)와 화면(`views/`) 분리, 화면 등록소(`views/registry.ts`)로 확장
- **v7** 반응형 데스크톱 레이아웃 — ≥900px 사이드바, 그 아래는 상단 탭 바
- **v8** 지식 요소 삭제 (참조하던 카드는 분류만 해제, 로그 유지)
- **v9** 데스크톱 화면별 다단 레이아웃 (진단 2열, 카드 폼/목록 분리)
- **v10** 카드 편집 (추가/편집 겸용 `ItemForm`)
- **v11** 테스트 스위트 (vitest + fake-indexeddb)
- **v12** KC별 목표 파지율 (Atlas 5부 "매트릭스") — 개념 단위로 복습 빈도 조절
- **v13** 덱 검색·필터 (타입/상태/KC/난이도 밴드)
- **v14** 필터된 덱으로 학습 세션 시작 — 덱 필터 결과를 세션 후보 풀로 바로 연결
- **v15** KC 선수지식 그래프 시각화 — prereqIds DAG를 SVG로, 숙달/준비/잠김 상태 표시
- **v16** 카드 일괄 작업 — 덱 필터 결과에서 여러 장을 골라 분류 재배정·삭제
- **v17** 단답형(short-answer) 카드 타입 — 문장 힌트 없이 완결된 질문에 직접 타이핑, 동의어 여러 개 허용
- **v18** 백로그 상한 + 휴가 모드 — 밀린 복습이 많아도 하루 상한만큼만, 신규 카드 도입 일시정지
- **v19** 채점 로그 부가 신호 — 응답 시간·응답 원문·선택지 인덱스·정책 버전 기록
- **v20** 활동 타입 인터리빙 제약 (같은 타입 연속 상한)
- **v21** 저품질 문항 자동 신고 (정답률이 한쪽 끝에 몰린 카드 표시)
- **v22** 콜드스타트 예시 덱 + 인터리빙 제약이 세션을 굶기지 않도록 단계적 양보
- **v23** 사전 테스트 — 아직 안 열린 KC의 문항을 세션 앞에 한 장, 페널티 없음(파생 상태에서 제외)
- **v24** 자기 설명 활동 타입 — 자기 말로 쓴 뒤 모범 답안과 대조해 자기 채점
- **v25** 오답 선택지 오개념 태깅 — 오답 즉시 진단 + 자주 걸리는 오개념 집계
- **v26** CSV 임포트 — 앞면·뒷면(+분류)만으로 카드 여러 장, 잘못된 줄만 건너뛰고 보고
- **v27** 학습 세션 기록 — 새로고침해도 이어서 하기, 예산 대비 실제 소화량 요약
- **v28** PWA 설치 + 로컬 복습 알림 — 홈 화면 설치·오프라인 앱 셸, 만기 카드가
  있을 때 브라우저 알림(탭이 열려 있으면 확실히 동작, 완전히 닫힌 상태에서는
  크로미움 계열·PWA 설치 시에만 최선형으로 동작)
- **v29** 같은 지식요소(KC)가 연속될 때 응답 전 자신감 질문을 한 번만 — 그
  구간 전체에 같은 값을 적용해 질문 횟수를 줄인다(KC가 없는 카드끼리는 묶지
  않는다)
- **v30** GitHub Pages 배포 + GitHub 저장소를 통한 기기 간 수동 동기화 —
  "데이터" 탭의 버튼을 누른 순간에만 GitHub의 파일 하나를 받아 병합하고, 합친
  전체를 다시 올린다(진짜 실시간은 아니다)

## GitHub 동기화 (v30)

서버 없이 GitHub 저장소 자체를 "데이터베이스"로 쓴다. 새로 만든 병합 로직은
없다 — 기존 백업 가져오기(병합 모드, `core/db.ts`의 `importAll('merge')`)를
그대로 태운다. id가 겹치면 들어오는 쪽이 이기는 put이고, 채점 로그의 id는
`crypto.randomUUID()`라 기기가 달라도 겹치지 않는다. 그래서 "원격을 받아
병합 → 합쳐진 전체를 다시 올림"이 실제로는 안전한 합집합이 된다.

**동작:** "데이터" 탭에서 GitHub owner/repo/파일 경로/개인 액세스 토큰(PAT)을
입력하고 "지금 동기화"를 누르면: ① GitHub Contents API로 원격 파일을 받는다
(없으면 첫 동기화로 취급) ② 이 앱의 백업 형식인지 검증 후 로컬에 병합
③ 병합된 전체 스냅샷을 다시 같은 파일에 커밋한다. 두 기기가 동시에 동기화하면
나중 커밋이 409/422로 거절되니 다시 누르면 된다.

**토큰 범위:** 이 저장소 하나에만 Contents: Read and write 권한을 준
fine-grained PAT를 쓴다. 토큰은 기기별로 그 브라우저의 localStorage에만
저장하고(`shell/githubSyncStorage.ts`) 절대 코드나 백업 파일에 넣지 않는다 —
공개 리포에 토큰이 박히면 그 리포에 쓸 수 있는 사람 누구나 그 토큰을 그대로
쓸 수 있게 된다. 다른 기기에서 동기화하려면 그 토큰을 그 기기 브라우저에
직접 한 번 입력해야 한다(자동으로 퍼지지 않는다 — 그게 안전한 이유다).

**퍼블릭 리포라는 것의 의미:** 이 저장소는 코드와 동기화 데이터를 같은 곳에
둔다. 즉 카드 내용·채점 로그·자기설명 응답 등 학습 기록이 커밋 이력에 그대로
남고, 인터넷 누구나 볼 수 있다(삭제해도 과거 커밋에는 남는다). 개인 용도로
쓰기로 하고 켠 기능이다 — 민감한 내용을 카드로 만들 계획이라면 저장소를
비공개로 바꾸거나 데이터만 별도 비공개 저장소로 분리하는 걸 고려할 것.

## 로그 포맷

학습 로그는 수년치 개인 기록이라 앱보다 오래 남는다. 내보내기 파일 하나만 있으면
다른 도구로도 읽을 수 있도록 형태를 여기 적어 둔다(내보내기: "데이터" 탭).

```jsonc
{
  "format": "learning-atlas-backup",
  "version": 1,          // 봉투 버전
  "dbVersion": 6,        // 내보낼 당시 IndexedDB 스키마 버전. 더 높은 파일은 가져오기 거부
  "exportedAt": "2026-09-05T...",
  "data": {
    "items": [], "interactions": [], "kcs": [], "sessions": [],
    "schedulerSettings": null, "studyPrefs": null
  }
}
```

`interactions` 한 건이 채점 한 번이다. **추가만 하고 절대 수정·삭제하지 않는다.**

| 필드 | 뜻 |
| --- | --- |
| `id`, `itemId`, `ts` | 식별자, 어떤 카드인지, 채점 시각(ISO-8601) |
| `grade` | `again` / `hard` / `good` / `easy` — FSRS·Elo 재생의 유일한 입력 |
| `confidence` | 답을 보기 전 자신감 1~3. 없으면 `null`(v0 로그) |
| `errorTag` | `concept`/`procedure`/`carelessness`/`time`. `again`일 때만 값이 있을 수 있다 |
| `latencyMs` | 문항이 뜬 뒤 채점까지 걸린 시간. 자신감 입력 단계는 뺀다 (v19+) |
| `response` | 사용자가 낸 답 원문. 빈칸은 ` \| `로 이음, 코드는 소스 전체 (v19+) |
| `selectedIndex` | 4지선다에서 고른 선택지 번호 (v19+) |
| `policyVersion` | 채점 당시 스케줄러 파라미터 식별자. 기본값이면 `"default"` (v19+) |
| `sessionId` | 어느 학습 세션에서 나온 채점인가 — `sessions`와 이어진다 (v27+) |
| `pretest` | 사전 테스트로 낸 문항이었는가 (v23+) |

v19 이후 필드는 전부 선택이다 — 그 이전 로그에는 아예 키가 없고, 활동 타입에 따라
낼 수 없는 신호도 있다(플래시카드에는 `response`가 없다). 읽는 쪽은 항상 "없을 수
있다"를 전제로 다뤄야 한다.

**무엇을 세느냐는 읽는 쪽의 결정이다.** 로그에서 지우는 건 없고, `pretest` 표시가
붙은 채점만 파생 학습 상태(FSRS 스케줄 · Elo 숙달도 · 캘리브레이션 · 문항 품질 ·
오개념 집계) 계산에서 빠진다. 아직 배우지 않은 걸 물어본 것이라 틀렸다고 학습자나
카드를 탓할 수 없기 때문이다. 반대로 "며칠 연속 했나" 같은 활동 집계에는 그대로
들어간다 — 실제로 푼 건 맞다. 이 구분은 `core/interactions.ts` 한 곳에만 있고,
스케줄러·통계 모듈은 이런 게 있다는 것조차 모른다.

## 구조

```
src/
  core/        도메인 모델, IndexedDB 접근, 백업, 캘리브레이션, 전역 상태(AtlasProvider)
  scheduler/   FSRS 래퍼, Elo, 세션 편성, 난이도 밴드 선택, 재적합 옵티마이저, 시뮬레이션
  activities/  활동 타입별 응답 UI, 오답 태그 선택
  analytics/   대시보드, 통계 집계
  shell/       탭 바 / 사이드바 / 해시 라우팅
  views/       학습 · 진단 · 카드 · 데이터 (+ registry)
```

새 화면(단계)을 추가하려면 `views/`에 컴포넌트 파일 하나를 만들고
`views/registry.ts`의 `VIEWS` 배열에 한 줄 등록하면 된다.

## 개발

```bash
npm install
npm run dev      # Vite 개발 서버
npm run build    # tsc -b && vite build
npm run lint     # oxlint
npm test         # vitest — 스케줄러·집계·백업·재생 결정성 (fake-indexeddb로 DB 계층까지)
```

`src/**/*.test.ts` 는 "로그를 재생하면 저장 순서·형태와 무관하게 같은 파생
상태가 나온다"는 이벤트 소싱 불변식(`core/eventSourcing.test.ts`)을 포함해
FSRS/Elo/세션 편성/캘리브레이션/백업을 고정한다.
